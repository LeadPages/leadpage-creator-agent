CHAPTER 08·~20 min·workshop: rightmodel

Right model

Sonnet has been doing every job. Some of those jobs don't need Sonnet. We sweep Haiku × Sonnet × Opus per subagent, measure pass rate, cost, and latency, and end with a different model in each slot.

Goal

Use the eval set from Chapter 07 as a benchmark. Run each subagent at each model tier. Build a quality-per-dollar table. Pick the cheapest model that doesn't regress quality.

The three knobs

The Claude model lineup, today:

(Opus 4.7 with 1M-token context is what's powering Claude Code right now. For agents that don't need to think across a huge codebase, Sonnet is usually fine and 5× cheaper.)

The sweep design

Our decomposed agent has three subagents (copywriter, designer, assembler). The naïve grid would be 3 models × 3 subagents = 27 cells, each running 6 tasks. Expensive.

Instead we do one subagent at a time: pin the others at Sonnet, vary one across {Haiku, Sonnet, Opus}, measure. That's 3 cells × 3 subagents = 9 cells. Each cell runs the 6-task eval. Total cost: about $1 the first time. 

// One subagent varies, others pinned to Sonnet baseline.
const baseline: Subagents = {
  copywriter: "claude-sonnet-4-6",
  designer:   "claude-sonnet-4-6",
  assembler:  "claude-sonnet-4-6",
};

for (const sub of ["copywriter", "designer", "assembler"]) {
  for (const model of MODELS) {
    const models = { ...baseline, [sub]: model };
    // run the agent on each eval task, grade, record pass_rate / cost / latency
  }
}

Try it (estimate: ~$1 in API spend, ~10 min)

bun run sweep

Or just compare two subagents quickly:

bun run sweep --pin assembler=claude-sonnet-4-6 --tasks T1,T2,T3

Reading the table

Three patterns are usually visible:

  • Copywriter: Haiku is fine. Writing 4 short JSON fields with strict rules is not hard. Sonnet doesn't help; Opus is a waste.
  • Designer: Sonnet is the floor. Haiku gets confused on at least one task (often T2 — the Stripe-style brief requires connecting "design feel" → palette). Sonnet handles it. Opus doesn't help further.
  • Assembler: Sonnet wins. Producing 200 lines of valid, internally-consistent HTML with inline CSS is the hardest single job in this agent. Haiku will sometimes miss the CTA, get the typography wrong, or skip a closing tag.

Adopt the recommendation and you cut your average request cost from ~$0.05 to ~$0.018 — about 65% off — with no measurable quality loss.

The 5% rule

"Cheapest model within 5% of the best pass rate" is a defensible default. Lower than that risks variance: a 100-trial eval at the cheaper tier might actually be 6% behind, not 5%. Higher than that and you start paying for headroom that doesn't ship.

What about thinking and effort?

The rightmodel workshop sweeps two more axes besides model: extended thinking (let the model generate a long internal reasoning trace before answering) and effort level (how hard the model should try). These can flip a Haiku-fails-this-task cell into a Haiku-passes cell — at the cost of more tokens.

For the Leadpage Creator, the gain from extended thinking is small — the tasks are short enough that the model doesn't need a long scratchpad. But for an agent doing harder reasoning (the StockPilot F2 task in the workshop, where the agent decides about under-stocking a promo), thinking is decisive. The point: sweep what matters for your workload. Model is the first axis to try; thinking/effort is the second.

The audit step — before you trust the sweep

Phase 1 of the rightmodel workshop is an audit of the eval suite. Sweep results are only as good as the eval underneath them. Things that quietly invalidate a sweep:

  • Task ordering effects. If the agent's behavior changes based on what it ran last, you're measuring noise.
  • Tiny dataset. 6 tasks is a tutorial dataset, not a benchmark. For real decisions, 30+.
  • Single trial. One run per cell hides variance. Aim for 3 trials per cell minimum.
  • Same-family judge. If both the agent and the LLM judge are Sonnet, Sonnet outputs will tend to score higher. Mitigations: swap judges, or have judge variance go into the report.
  • Pass thresholds with no calibration. A 3.5/5 cutoff might be too easy or too hard. Look at the distribution of judge scores before trusting "pass rate".

Checkpoint
The sweep table shows your copywriter getting 83% on Haiku, 83% on Sonnet, and 83% on Opus. You decide to use Haiku. Six months later the eval set has grown to 60 tasks and Haiku now scores 78% while Sonnet scores 88%. Which thing should you NOT do?
Tweaking the prompt of the model that lost in order to make it look better is exactly the bias the rightmodel audit warns about: you've started fitting the eval rather than measuring against it. If the bigger model actually wins, ship the bigger model. If the smaller model is losing on specific tasks, fix the smaller model's prompt, then re-run the sweep — not the other way around.
