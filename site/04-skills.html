CHAPTER 04·~25 min·workshop: agent-decomposition

Skills

Some instructions are too big for the system prompt and too rule-shaped to be a tool. A skill is a markdown file the agent loads when it decides it needs it — paying for the tokens only on the turns where they're useful.

Goal

Move the copywriting rules and the hero-layout patterns out of the system prompt and into two skill files. Add a load_skill tool. Watch the agent decide which skills to load. End with a smaller system prompt and better, more consistent output.

The shape of a skill

A skill is a plain markdown file with a tiny YAML frontmatter — a name and a one-line description the model reads when deciding whether to load this skill. The body is whatever instructions the skill encodes. 

---
name: conversion-copy
description: Rules for writing landing-page copy that converts — headline shape,
  subhead pattern, value prop structure, CTA voice. Load when generating page copy.
---

# Conversion copywriting rules

These are the rules the copywriter follows. They're opinionated on purpose.

## Headline (`<h1>`)
- Lead with the outcome, not the product.
- One promise. Two promises convert on neither.
- 6–12 words.
- Avoid: "Unlock", "Revolutionize", "Empower", "AI-powered".

## CTA
- Verb + specific outcome. "Try a box" beats "Get Started".
- 2-4 words.
- One primary CTA on the page.

[... full file in src/skills/conversion-copy.md ...]

The second skill, hero-patterns.md, encodes which hero layout to use when. (Same shape, different content — go look at src/skills/hero-patterns.md.)

The load_skill tool

We add one new tool. Its description lists every available skill — that's how the model knows which ones exist. The skill bodies themselves never get sent until the agent asks for them. 

{
  name: "load_skill",
  description:
    "Load the body of a skill into context. Use this when you decide a skill is " +
    "relevant to the current task. Available skills:\n" +
    SKILLS.map(s => `  - ${s.name}: ${s.description}`).join("\n"),
  input_schema: {
    type: "object",
    properties: {
      name: { type: "string", enum: SKILLS.map(s => s.name) },
    },
    required: ["name"],
  },
}

Two design choices worth noticing here:

  • The skill list is in the tool description. The skill bodies are loaded on demand. Big payoff: a skill can be 800 lines without costing 800 lines on every request.
  • The input schema uses enum. The model literally cannot ask for a skill that doesn't exist. (Without the enum, you'd have to handle "skill not found" — fine, just more code.)

The shrunken system prompt

Look at what's left in the prompt. It used to spell out the page structure, the typography rules, the CTA style, and the headline format. Now it just tells the agent where the rules live: 

const SYSTEM = `
You design and write landing pages.

You have two tools:
- load_skill(name): pulls a chunk of instructions into context. Skills you
  can load are listed in the tool description. Load them when relevant —
  don't load everything up front.
- save_page(filename, html): writes the final document and stops the loop.

For every brief, follow this routine:
1. Decide which skills are relevant to this brief.
2. Load them with load_skill (call once per skill, before generating).
3. Generate the complete HTML.
4. Call save_page exactly once with the final document.
`.trim();

Ten lines. The agent gets the actual style rules only when it needs them, and the rules can grow arbitrarily without making every request slower or more expensive.

Try it

bun run skills "vegan meal kits for busy parents"

The terminal will show which skills the agent decided to load:

turn 1 → load_skill(hero-patterns) → load_skill(conversion-copy) turn 2 → save_page turns: 2, skills loaded: hero-patterns, conversion-copy ✓ saved to /…/out/vegan-meal-kits.html

Notice the model batched both load_skill calls into a single turn — that's parallel tool use. Faster than asking for one, waiting, asking for the next.

Now run it with a brief where neither skill clearly applies:

bun run skills "a flat HTML coming-soon page, just a logo and an email field"

Expected:

turn 1 → save_page turns: 1, skills loaded: (none) ✓ saved to /…/out/coming-soon.html

No skills loaded — the agent decided neither was relevant for a one-field email-capture page. That's the agent using the skill descriptions (and the prompt's explicit examples) to decide, instead of always loading everything.

When to use a skill vs a tool vs a longer system prompt

If it's…Use a…Because…
Always relevant, fits in <30 lines System prompt Cheap, present every turn, no cognitive overhead for the model.
Big body of rules / patterns / examples Skill Loaded only when relevant. Can be hundreds of lines without costing tokens on unrelated requests.
External data lookup or side effect Tool The model can't know it / can't do it. Code in your repo handles it.
A sub-task with its own context and goal Subagent (Ch 05) Separating contexts keeps each one focused. A subagent's failure mode is local.
The decomposition workshop's heuristic, in one line

"If you find yourself writing 'always do X before Y' in the system prompt — that's a skill. If the agent never reads it for a given request, the prompt got too big. Move the rule into a skill, leave a line in the system prompt that says when to load it."

Why skills beat one big prompt — measured

When we put this through the eval set in Chapter 07, the skills-version of the agent will get higher conversion-quality scores than the monolith-prompt version on the briefs that needed the rules, and indistinguishable scores on the briefs that didn't — but at a lower average input token count. The pattern shows up in the StockPilot workshop too: their decomposition shrinks a 402-line prompt to 15 lines, and the agent's score goes from 71% to 92%. The knowledge didn't shrink (400 lines of skills replaced 400 lines of prompt). The difference is when they're in context.

Checkpoint
Why is it better to put conversion-copy.md in a skill, instead of just pasting its contents into the system prompt?
The system prompt is sent on every turn. Skills load on demand. For a 600-line copywriting reference, that's the difference between paying for 600 lines on every request and paying for them only on the ~70% of requests where the agent decides they apply. The token savings matter, but the deeper effect is on the model's focus: the system prompt is what the model uses to decide what kind of request this is, and a 600-line prompt drowns out the 1-line user message.
