CHAPTER 05·~30 min·workshop: agent-decomposition

Decomposition

Three specialists with their own focused contexts beat one generalist trying to hold the whole job. We split the Leadpage agent into a copywriter, a designer, and an assembler, with an orchestrator that routes between them.

Goal

Replace the single agent with an orchestrator + three subagents. Each subagent has its own narrowed system prompt, its own context window, and its own output shape. Understand when to add a subagent — and when adding one is the wrong move.

The before/after

BEFORE                              AFTER

┌─────────────────┐                ┌──────────────────┐
│                 │                │   orchestrator   │
│  one agent      │                │   (your code)    │
│                 │                └────────┬─────────┘
│  - read brief   │                         │
│  - pick copy    │                ┌────────┼────────┐
│  - pick design  │                ▼        ▼        ▼
│  - emit HTML    │           ┌─────┐  ┌─────┐  ┌──────┐
│                 │           │ copy│  │ dsgn│  │ asm  │
└─────────────────┘           └─────┘  └─────┘  └──────┘
                              JSON     JSON      HTML

The "after" isn't obviously better — it's three calls instead of one, which means three times the round-trips. So why decompose?

  • Each subagent has one job, with a system prompt that's about that job only. The copywriter never gets distracted by layout decisions. The designer never has to think about CTA verbs.
  • Each subagent's context is small and focused. The copywriter doesn't see hero patterns; the designer doesn't see the whole copywriting reference.
  • Each subagent can be a different model. Copywriting is a Haiku-class task. Layout might be a Sonnet task. (Chapter 08 will measure this.)
  • Failures are local. If the designer returns invalid JSON, you retry just the designer. The copywriter's good output isn't thrown away.
  • Each subagent's output is structured, so the next stage doesn't have to parse free-form text.

The decision framework, properly

This is the chart from the StockPilot workshop — the canonical rubric for "is this thing a tool, a skill, or a subagent?":

ConstructCostUse when
Tool cheap, stateless You have data the model can't have, or a side effect only your code can perform. Output is small, structured.
Skill cheap, doc-shaped You have a body of rules / patterns / examples that's too big for the system prompt and not relevant on every request.
Subagent another full LLM call The work has its own goal, its own context, and its own decision space — and the result of the subagent is itself a small artifact (JSON, paragraphs, a number range), not a one-token answer.
The anti-pattern: the one-number subagent

If your subagent reads the input and returns "yes" or "no" or "47", it should be a tool — or a turn of the parent agent's own loop. Subagents are expensive because they spin up a fresh context; if the answer is a token, that's a price you didn't have to pay.

How a subagent works (when you're not on the managed-agent platform)

On Claude Managed Agents, sub-agents are a first-class platform feature: they have their own threads, their own memory, their own observability. We get to that in Chapter 10. For now we're still in plain SDK land, and a "subagent" is just a separate messages.create call with a focused system prompt — managed by your code, invoked from your orchestrator function. 

async function copywriter(brief: string, primary_goal?: string): Promise {
  const rules = await readFile("src/skills/conversion-copy.md", "utf8");

  const response = await client.messages.create({
    model: DEFAULT_MODEL,
    max_tokens: 1024,
    system: `
You are a conversion copywriter. Return ONLY a JSON object with fields:
headline, subhead, body (array of 2 strings), cta.

The CTA MUST drive the primary_goal — "book demo" → "Book a demo", not
"Start free trial". Never invent a different conversion path.

Apply these rules strictly:

${rules}
`.trim(),
    messages: [{
      role: "user",
      content:
        `Brief: ${brief}\n` +
        (primary_goal ? `Primary goal: ${primary_goal}\n` : "") +
        `\nReturn the JSON.`,
    }],
  });

  return extractJson(firstText(response.content));
}

Three things to notice:

  1. Structured output as JSON. The copywriter never returns prose — it returns a JSON object the orchestrator can read. The schema is encoded in the system prompt; in production you'd use the API's response_format or output_schema to enforce it.
  2. The skill body is inlined into the subagent's system prompt, because the copywriter always needs the copywriting rules. There's no need for a load_skill tool here.
  3. No agent loop. This is a one-shot call. The subagent doesn't have tools. Its only job is to produce structured copy.

The orchestrator

async function orchestrate(brief: string, primary_goal?: string) {
  const copy   = await copywriter(brief, primary_goal);
  const design = await designer(brief, copy, primary_goal);
  const html   = await assembler(copy, design);

  await writeFile("out/05-decomposition.html", html, "utf8");
}

That's the whole orchestrator. Three lines. It's just Promise-and-await glue — no LLM call of its own. The orchestrator could be an LLM-driven agent (one that uses an inner loop to choose which subagent to call next), but for this workflow the order is always the same, so making it a model decision would be needless flexibility and a needless API call.

Code where you can, model where you must

If the workflow is fixed (copy then design then assemble), hardcode the order. Save the LLM for the parts that are actually decisions. This is the most common over-engineering pattern in agent-land: putting a model in every decision slot, even the ones that don't have decisions.

Try it

bun run decompose "vegan meal kits for busy parents"

You'll see each subagent's output as it goes:

▸ brief: vegan meal kits for busy parents ▸ → copywriter headline: "Plant-based dinners that don't ask for thirty minutes you don't have." cta: "Try your first box" ▸ → designer palette: #2f7a4a, #f6f0e4, #1d1b18, #d96e2b, #c5dfd2 layout: split ▸ → assembler ✓ /…/out/05-decomposition.html

Compare that output side-by-side with out/04-skills.html. The 05 version usually has a cleaner separation between the copy (tight, on-brief) and the design (consistent palette, layout chosen with intent).

Three things to look for when this is going well

  1. Each subagent's output is small. Copy is ~150 tokens, design is ~80, assembler emits the HTML. If a subagent's output starts looking like prose + answer, it's drifting — tighten the prompt.
  2. The orchestrator never wears two hats. If you find your orchestrator function doing string parsing or business logic on what came back, that work probably belongs in one of the subagents.
  3. You can swap one subagent's model. Try setting the copywriter to Haiku and the designer to Sonnet. If the page quality holds, congratulations — you just halved that subagent's cost. Chapter 08 systematizes this.

When NOT to decompose

Decomposition isn't free. Each subagent is another API round-trip and another chance for things to fail. Don't decompose when:

  • The whole task fits comfortably in one prompt and one response (~500 tokens, no branching). A "rephrase this sentence" job doesn't want three agents.
  • The subagents would need to share a lot of context. If each subagent has to be told the whole story, decomposition just made everything slower.
  • You can't articulate what each subagent decides. If you can't write down "the copywriter picks the headline; the designer picks the palette" cleanly, the boundaries are wrong.

Reference to the workshop

The StockPilot workshop (agent-decomposition/ in the CWC repo) does this exact pattern at production scale: takes an inventory agent with a 402-line monolith prompt and three hardcoded subagents, decomposes it into skills + code execution + one well-placed subagent, runs evals after every change, and lands at 92% pass rate (up from 71%). The takeaway lines from that workshop apply directly to ours: "The knowledge didn't shrink — 402 prompt lines became 400 skill lines. The difference is when they're in context."

Checkpoint
A teammate suggests adding a fourth subagent: cta_optimizer that takes the headline and returns the "best" CTA verb (one of: "Try", "Get", "Start", "See"). Which thing is it actually?
The smell test from the StockPilot workshop: "Subagent's output is one number? → it shouldn't be a subagent." Here the output is one of four enum values — even smaller. The cost of spinning up a subagent is the same as a full LLM call, but the value is a string. That's an anti-pattern. Either fold it into the copywriter (it's already deciding on copy), or expose it as a deterministic tool with a lookup table.
