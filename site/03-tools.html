CHAPTER 03·~25 min·tool use, the agent loop

Tools

We hand Claude two functions — fetch_brand_colors and save_page — and write the loop that lets it actually call them. This is the moment the program goes from "LLM call" to "agent."

Goal

Implement an agent loop with two real tools. By the end you'll understand stop_reason: "tool_use", the shape of a tool_result, and the rule of thumb for what should be a tool vs what shouldn't.

The loop, in pictures

┌────────────┐   user.message + tools=[…]
│   You      │ ─────────────────────────────▶ ┌──────────┐
│            │                                │  Claude  │
│            │ ◀──────── tool_use ─────────── │          │
│            │   "call fetch_brand_colors(    └──────────┘
│            │    domain='stripe.com')"
│            │
│  runs tool │
│  → palette │
│            │
│            │   tool_result for that id ───▶ ┌──────────┐
│            │                                │  Claude  │
│            │ ◀───── tool_use (save_page) ── │          │
│            │   "call save_page(             └──────────┘
│            │    filename=…, html=…)"
│            │
│  runs tool │
│  → /path/  │
│            │
│            │   tool_result ───────────────▶ ┌──────────┐
│            │                                │  Claude  │
│            │ ◀──── text + end_turn ──────── │          │
└────────────┘   "Done! Saved to /path"       └──────────┘

Three turns. Six events. Two tools called. The agent's reasoning is invisible — all you see is what it asks for and what you give back. Your job as a developer is to (a) describe the tools accurately and (b) execute the calls faithfully. Claude does the rest.

Step 1: describe the tools

Tools are JSON-Schema descriptions of functions. Claude reads these descriptions and decides when (and how) to call them. The description text matters as much as the schema — it's how the model knows what the tool is for. 

const TOOLS: Anthropic.Messages.Tool[] = [
  {
    name: "fetch_brand_colors",
    description:
      "Look up a brand's color palette by domain. Returns up to 5 hex colors, " +
      "primary first. Use only if the user mentions an existing brand.",
    input_schema: {
      type: "object",
      properties: {
        domain: { type: "string", description: 'The brand\'s domain, e.g. "stripe.com"' },
      },
      required: ["domain"],
    },
  },
  {
    name: "save_page",
    description:
      "Write the final landing page HTML to disk and return its absolute path. " +
      "Call once at the end with the complete document.",
    input_schema: {
      type: "object",
      properties: {
        filename: { type: "string", description: 'A short filename like "vegan-meal-kits.html"' },
        html:     { type: "string", description: "The complete <!doctype html> document." },
      },
      required: ["filename", "html"],
    },
  },
];
Write tool descriptions for a coworker, not a parser.

The model has read tens of thousands of API docs and follows the same conventions. "Returns up to 5 hex colors, primary first" tells the model what to expect — which means it'll write less defensive prompt code than if you just said "returns colors."

max_tokens has to fit the whole tool call

When Claude calls save_page(filename, html), the full HTML page is serialized as the html parameter of the tool_use block — and every token of that HTML counts against max_tokens. A 4096-token ceiling fits a tight page, but a verbose model on a complex brief will hit stop_reason: "max_tokens" mid-tool-call, leaving the save_page call malformed and the file never written. We use 16384 for headroom; the system prompt also tells the model to keep the page under 150 lines.

Step 2: write the tool functions

Tool implementations are just regular TypeScript. They take an input object (matching the schema), do something, and return whatever they want. Whatever you return gets JSON.stringify'd and sent back to Claude as the tool result. 

const KNOWN_BRANDS: Record = {
  "stripe.com":    ["#635bff", "#0a2540", "#fff", "#7a73ff", "#425466"],
  "linear.app":    ["#5e6ad2", "#0f0f12", "#fff", "#8a8df0", "#1c1c20"],
  "anthropic.com": ["#d97757", "#f0eee6", "#1f1f1d", "#3a3a36", "#f4ddc8"],
};

async function fetch_brand_colors(input: { domain: string }) {
  const palette = KNOWN_BRANDS[input.domain.toLowerCase()];
  if (palette) return { palette };
  return {
    palette: ["#1d1b18", "#d96e2b", "#faf8f4", "#4a463f", "#e6dfd1"],
    note: "domain not in cache, returning a warm editorial palette",
  };
}

async function save_page(input: { filename: string; html: string }) {
  await mkdir("out", { recursive: true });
  const path = resolve("out", input.filename);
  await writeFile(path, input.html, "utf8");
  return { path };
}
Why the brand lookup is mocked

A real fetch_brand_colors would scrape the site or call a service. We hardcode three brands so the agent's behavior is stable while you're learning. In Chapter 09 we wire it up to a real MCP server. The agent doesn't know the difference — that's the point.

Step 3: the loop

The loop is the heart of the agent. Run a call, check stop_reason: if it's "tool_use", execute the tools the model asked for and send the results back. Otherwise, stop. 

const messages: Anthropic.Messages.MessageParam[] = [
  { role: "user", content: `Create a landing page for: ${topic}` },
];

while (true) {
  const response = await client.messages.create({
    model: DEFAULT_MODEL,
    max_tokens: 16384,    // ← the HTML lives inside save_page's tool_use,
                          //   which counts against output tokens
    system: PROMPT_WITH_TOOLS,
    tools: TOOLS,
    messages,
  });

  // 1. Remember what Claude said this turn.
  messages.push({ role: "assistant", content: response.content });

  // 2. If it didn't ask for any tools, we're done.
  if (response.stop_reason !== "tool_use") break;

  // 3. Otherwise, run every tool_use block and gather the results.
  const tool_uses = response.content.filter(
    (b): b is Anthropic.Messages.ToolUseBlock => b.type === "tool_use",
  );

  const tool_results = [];
  for (const use of tool_uses) {
    const result = await runTool(use.name, use.input);
    tool_results.push({
      type: "tool_result",
      tool_use_id: use.id,
      content: JSON.stringify(result),
    });
  }

  // 4. Hand the results back as the next user turn.
  messages.push({ role: "user", content: tool_results });
}

Three things to notice about this loop:

  1. The conversation is just an array. Each turn appends two messages — one assistant, one user (with tool results). The model has no other memory. If you don't push, the model forgets.
  2. tool_use_id matters. When you send back a tool_result, it has to match the id Claude sent in the tool_use block. The model can request multiple tools in one turn — you have to return one result per id.
  3. There's no max iterations in this loop. That's fine for learning, dangerous for production. We add it in Chapter 09.

Tool vs not-a-tool: the smell test

Things that should be tools:

  • Reading data the model can't possibly know (today's date, a database row, a brand's actual colors).
  • Writing side effects the model shouldn't simulate (saving a file, sending an email, charging a card).
  • Calling an external API where the output is small (a price, a status, a row).

Things that shouldn't be tools — even though you could make them tools:

  • Decisions the model can make itself. "Pick a font" is not a tool. The model can pick a font.
  • Operations that return more than a couple of thousand tokens. Those eat context. Better: have the model write code and execute it.
  • Anything that's actually a sub-task with branching logic. That's a subagent's job (Chapter 05).
From the StockPilot workshop

"Tool returns >2k tokens? → code execution instead. Writing 'always do X before Y' in the prompt? → skill. Subagent's output is one number? → it shouldn't be a subagent."

You'll see all three of those flips happen before Chapter 10.

The output is noticeably better — the agent picks real palettes, formats consistently, and saves files itself. But the system prompt is still doing too much. It's mixing format requirements ("emit <!doctype html>") with style guidance ("warm accent color") with output discipline ("call save_page exactly once"). Three different things, all in one wall of text.

Chapter 04 moves the style guidance into a skill — a markdown file the agent loads when it wants to. That's the second big lever in the decomposition framework.

Checkpoint
The agent calls fetch_brand_colors and you return a palette. Why do you have to also pass the previous assistant message back on the next turn?
This is the most common source of "my agent loop hangs" bugs. The API is stateless: every call sends the entire conversation. Each tool_result references a tool_use_id from an assistant turn — so that assistant turn has to be in the messages array, or the model has no record of having asked.
