CHAPTER 07·~30 min·workshop: eval-driven-agent-development

Evals

"It feels better" isn't a number. We build a six-task test set and a two-layer grader, run it against the agent we have, save the score as the baseline. From here on, every change has a delta.

Goal

Stop vibing. Build an eval suite the rest of the tutorial uses as ground truth. After this chapter, when a future chapter says "this is better," there will be a number behind that claim.

Why evals before everything else

Every chapter so far has been "now the agent has X, isn't this better?" The honest answer is: we don't know. Generative outputs are easy to over-rate when you wrote the prompt yourself. You remember the run that looked great. You forget the run that hung on a footer.

An eval suite is three pieces:

  1. A dataset of representative inputs.
  2. A grader that scores each output.
  3. A baseline — the score before your change.

With those, every prompt edit becomes a number, and the question "did this help?" becomes answerable.

The dataset

Six tasks. Just enough variety that a single trick won't ace all of them. Each task has the brief, the words we expect to see in the output, and the page's primary goal (so the LLM judge knows what to weight).

  "tasks": [

    { "id": "T2-saas-accountants","brief": "a SaaS dashboard for solo accountants — feels like Stripe's design", ... },

    { "id": "T5-coming-soon",     "brief": "a flat coming-soon splash, just a logo and an email field, for a B2B SaaS in stealth", ... },
    { "id": "T6-pricing-plain",   "brief": "a single pricing page for a consulting firm — three tiers, no marketing fluff", ... }

}
What makes a good eval task
  • Specific — "vegan meal kits for busy parents" beats "a food page".
  • Adversarial-ish — at least one task that breaks your prompt's assumptions (T5: no hero needed, just an email field).
  • Covers what matters — your suite should include the kinds of briefs you actually get.
  • Stable — don't rewrite the dataset every time the agent fails it. The dataset is the spec.

The grader, two layers

The eval-driven workshop's pattern: combine fast deterministic checks with an LLM judge. Each layer catches what the other misses.

LayerChecksWhy it's there
Programmatic Has <!doctype html>; has an <h1> (4–16 words); has a button/link CTA (≤6 words); has ≥1 body paragraph; mentions at least half the must_mention words. Catches structural failures cheaply. If this fails, we don't even ask the judge.
LLM-as-judge Three 1-5 scores: conversion_quality, brand_fit, layout_appropriate, plus a short rationale. Pass = average ≥ 3.5. Catches the things only a reader can catch — tone, specificity, whether the layout actually matches what the brief asked for. 
// Programmatic
export function gradeProgrammatic(task: Task, html: string): ProgrammaticScore {
  const has_doctype  = /<!doctype html/i.test(html);
  const h1           = (html.match(/<h1[^>]*>([\s\S]*?)<\/h1>/i) || [])[1] || "";
  const has_h1       = h1.replace(/<[^>]*>/g, "").trim().length > 0;
  const cta          = html.match(/<(button|a)[^>]*>([\s\S]*?)<\/\1>/i);
  const has_cta      = !!cta;
  const mention_hits = task.must_mention.filter((w) =>
                         html.toLowerCase().includes(w.toLowerCase())).length;
  const pass = has_doctype && has_h1 && has_cta &&
               mention_hits >= Math.ceil(task.must_mention.length / 2);
  return { has_doctype, has_h1, has_cta, mention_hits, pass, /* ... */ };
}

2. brand_fit: design matches the brief?
3. layout_appropriate: hero pattern right for this kind of page?

Return ONLY: {"conversion_quality": N, "brand_fit": N, "layout_appropriate": N,
"rationale": "one sentence"}.
`;

The LLM judge has biases — name them

From the rightmodel/eval-audit checklist: LLM judges tend to over-rate longer outputs, well-formatted outputs, and outputs written by the same model family as the judge. Mitigations: use a different model family as judge than as agent, score absolutely (not pairwise), and check the rationale text for sycophantic language.

Running the eval

The runner loops every task through the current agent, scores it, and prints a table:

Try it

bun run eval                # uses the v05 decomposition agent
bun run eval --baseline     # save this run as the baseline

Expected output:

▸ agent: v05 tasks: 6 T1-veg-meals prog ✓ judge ✓ (3.7/5) 9.4s T2-saas-accountants prog ✓ judge ✓ (4.0/5) 10.1s T3-marathon prog ✓ judge ✓ (3.7/5) 8.9s T4-indie-game prog ✓ judge ✓ (3.5/5) 9.0s T5-coming-soon prog ✓ judge ✗ (3.0/5) 6.2s ← too much hero T6-pricing-plain prog ✓ judge ✓ (3.7/5) 9.6s ── score: 5 / 6 (83%) ↳ saved as baseline

Iterate. Measure. Stop arguing.

Now the workflow gets disciplined. You make a change (edit a system prompt, swap a model, refactor a subagent). You run the eval. You see what flipped. 

# scenario: T5 (coming-soon) failed. We add a hint in the orchestrator
# to skip the hero on minimal briefs. Then:

bun run eval

▸ agent: v05   tasks: 6
  T1-veg-meals          prog ✓  judge ✓ (3.7/5)  …
  T2-saas-accountants   prog ✓  judge ✓ (4.0/5)  …
  T3-marathon           prog ✓  judge ✓ (3.7/5)  …
  T4-indie-game         prog ✓  judge ✓ (3.7/5)  …
  T5-coming-soon        prog ✓  judge ✓ (4.0/5)  …   ← flipped!
  T6-pricing-plain      prog ✓  judge ✓ (3.7/5)  …

  ── score: 6 / 6 (100%)
  ↳ baseline was 5/6 (+1)
     → PASS  T5-coming-soon

That last line — "→ PASS T5-coming-soon" — is what changes the feedback loop. Before, you'd push the change and ask a teammate "is this better?" Now you push the change and look at the diff.

Comparing two versions of the agent

The eval runner takes an --agent flag. You can compare v02 (the first-call baseline) and v05 (the decomposition version): 

bun run eval --agent v02 --baseline   # save v02 score as baseline
bun run eval --agent v05              # run v05, compare

This is how you justify the complexity. If decomposition (v05) doesn't beat the first-call (v02) by a meaningful margin on the eval set, you've been spending architecture for nothing.

Calibrate the dataset, then leave it alone

Spend an hour up front making the dataset good. After that, don't touch it — every change you make to the dataset invalidates every prior baseline. New behavior to test? Add a new task with a new id. Old behavior changed? Decide whether the old task is still the spec.

Reference: the eval-driven-agent-development workshop

The CWC workshop this is modeled on takes a slide-deck-generating agent through six rounds — naive, visual, typography, palette, density, QA-loop — and measures each one. Same shape as ours: a programmatic layer over the .pptx XML, an LLM-as-judge over the rendered slides. The workshop's agent goes from a 36% baseline to a 78% final score, every step justified by a measurement. The principle is the same whether the artifact is a deck, a page, or a SQL query: measure or move on.

How this tutorial got the code you're reading

The eval set above isn't decorative — running it on the Chapter 05 agent surfaced two bugs that shaped the code in this repo.

T4 (indie-game) failed because the assembler subagent buried the "Wishlist on Steam" CTA at the bottom of the page. The judge gave 3.3/5 with the rationale "no visible CTA button" — technically wrong (it existed), practically right (it was below the fold). Fix: a single sentence in the assembler's system prompt requiring the CTA to land in the hero. T4 flipped PASS at 4.3/5.

T2 (saas-accountants) failed because the copywriter produced "Start your free trial" instead of "Book a demo" — the task's primary_goal was "book demo", but that field was in the dataset and the agent never saw it. The orchestrator passed only the natural-language brief through to the copywriter. Fix: thread primary_goal from the orchestrator into the copywriter and designer (see Chapter 5's signatures — that's why they take an optional primary_goal argument).

Neither fix would have happened from staring at the code. The eval did the discovering. The point of this chapter is exactly that: eval-driven dev isn't a hypothetical workflow — it's how the code you're reading got written.

Checkpoint
Your eval score jumps from 67% to 92% after a prompt change you made. A teammate asks "but is the agent actually better?" What's the right thing to do before you celebrate?
The rightmodel workshop's audit checklist makes this explicit: run trials per cell to estimate variance, look at per-task flips rather than just totals, and spot-check the judge by reading a few rationales. A 25-point jump is suspicious until you've actually looked at what changed.
