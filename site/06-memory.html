CHAPTER 06·~25 min·workshop: agents-that-remember

Memory

Right now, every run starts from zero. The agent doesn't know what the user told it five minutes ago. We give it a brand-kit memory store so it can carry facts across sessions — the SDK-only version here, and a peek at how Claude Managed Agents formalize the same shape.

Goal

Add two tools — remember and recall_all — backed by a JSON file. Show the "goldfish baseline" (no memory), then turn it on and see the agent reference earlier facts. Map what we built onto the managed-agents memory_store concept.

The goldfish baseline

Sessions are isolated by design — every API call sends the entire conversation in messages. If you start a new session, the agent has zero memory of any previous one. That's what the agents-that-remember workshop calls the "goldfish": cute, but useless for anything that has to know your brand by Tuesday. 

session A: "I'm building for FreshLeaf — green & cream, warm voice"
session A: agent makes a page. Knows everything.
                  ↓
              [session ends]
                  ↓
session B: "make me another page for FreshLeaf"
session B: agent: "What's FreshLeaf? What palette? What voice?"

The shape of the fix

Give the agent a store — a place outside the session — that it can write to and read from. Mount that same store into every session, and the agent has continuity. The simplest possible store is a JSON file on disk: 

{
  "brand_name": "FreshLeaf",
  "palette": ["#2f7a4a", "#f6f0e4", "#1d1b18"],
  "voice": "warm, specific, parent-friendly",
  "audience": "busy parents"
}

The agent gets two tools. recall_all reads the file. remember(key, value) writes one entry. The system prompt tells the agent to call recall_all first on every session, and to call remember whenever the user mentions a fact. 

const TOOLS = [
  {
    name: "remember",
    description: "Save a fact about the user's brand to persistent memory.",
    input_schema: {
      type: "object",
      properties: {
        key:   { type: "string", description: "A short slug like 'palette' or 'voice'." },
        value: { description: "Any JSON-serializable value." },
      },
      required: ["key", "value"],
    },
  },
  {
    name: "recall_all",
    description: "Return everything currently in the brand-kit store.",
    input_schema: { type: "object", properties: {} },
  },
];

Try it — three sessions, one brand

rm -rf .memory   # start fresh

bun run memory "I'm building a page for FreshLeaf — vegan meal kits.
                Use green and cream, warm parent-friendly voice."

bun run memory "Make me another page for the FreshLeaf holiday gift box."

bun run memory "Show me what you know about FreshLeaf."

Watch the tool calls:

▸ "I'm building a page for FreshLeaf..." → recall_all({}) → remember({"key":"brand_name","value":"FreshLeaf"}) → remember({"key":"palette","value":["#2f7a4a", "#f6f0e4"]}) → remember({"key":"voice","value":"warm, specific, parent-friendly"}) ▸ "Make me another page for the FreshLeaf holiday gift box." → recall_all({}) (agent now sees brand_name, palette, voice — uses them) ▸ "Show me what you know about FreshLeaf." → recall_all({}) I know that FreshLeaf is a vegan meal kit brand. Its palette is green (#2f7a4a) and cream (#f6f0e4) with charcoal accents…

Look at .memory/brand-kit.json between runs to see what the agent decided to save.

What's a good thing to remember?

Memory is small. Keep it as facts, not transcripts. Good keys:

  • Facts you keep being asked the same question about — palette, voice, audience, primary CTA verb.
  • User preferences — "always avoid stock photography", "no Comic Sans".
  • Constraints discovered the hard way — "the legal team requires a privacy link in the footer".

Bad things to store:

  • Whole conversation transcripts. Memory isn't a log. Logs go somewhere else.
  • Anything time-sensitive without a timestamp. "We're running a promo this week" rots into nonsense by next month.
  • Anything you'd be unhappy seeing leaked. Treat the memory store as private but not secret — it lives outside the model's training data and is visible to anyone with API access.

Mapping to Claude Managed Agents

On the managed-agents platform, the same idea has a first-class primitive: a memory store — a persistent file-system that the agent reads from and writes to across sessions. You create it once and attach it to each new session as a "resource": 

ant beta:memory-stores create \
  --name "brand-kit" \
  --description "FreshLeaf brand kit"

ant beta:sessions create \
  --agent "$AGENT" --environment-id "$ENV" \
  --resource '{
    "type": "memory_store",
    "memory_store_id": "mem_...",
    "prompt": "Track the user'\''s brand kit.",
    "access": "read_write"
  }'

The prompt field gets injected into the agent's system prompt — it tells the agent how to use this store. That's the lever you tune, exactly like we tuned ours with the "always recall_all first" sentence above.

Dreaming — the consolidation step

The agents-that-remember workshop has a second concept: Dreaming. The idea is: after a few sessions, the live memory store gets messy. Maybe the agent stored the same fact three different ways, or wrote prose where it should have written a key. Dreaming is a batch job that reads the live store plus the transcripts and writes a new, distilled store. You then swap the new store in for future sessions. 

ant beta:dreams create \
  --model claude-opus-4-7 \
  --input "{\"type\":\"memory_store\",\"memory_store_id\":\"$MEM\"}" \
  --input "{\"type\":\"sessions\",\"session_ids\":[\"$SESS1\",\"$SESS2\"]}" \
  --instructions "I am building landing pages for FreshLeaf — keep the
                  facts that affect generated pages; drop conversational fluff."

For the SDK-only version of our Leadpage Creator, you'd replicate this with a periodic offline script: read .memory/*.json, read any saved conversation logs, run a model over them with the same kind of instructions, write a cleaned-up file. Conceptually identical to managed Dreaming, just with you running the cron.

When to reach for which

Memory store when the agent needs continuity right now. Dreaming when the store has gotten messy enough that the agent's recall is suffering — or when you want to absorb a backlog of transcripts into a structured form.

Checkpoint
You're considering storing every user message and every page the agent produces in the memory store, "so the agent has full history". Which line in this chapter is the strongest argument against doing that?
The memory store sits in every session's context — its job is to be the agent's working knowledge, not its history. If you stuff transcripts into it, every future session pays input tokens to re-read them, and the agent has to scan past noise to find facts. For "what happened last Tuesday," reach for a database or an audit log; for "what's the user's palette," reach for the memory store. (The Dreaming workshop is essentially built on this observation: the periodic batch turns the noisy log-like things into clean fact-shaped things.)
