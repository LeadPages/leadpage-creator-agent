CHAPTER 09·~25 min·workshop: production-ready-agent

Production

Five things change between "agent that works on my laptop" and "agent other people rely on": you stream output, you retry transient errors, you gate destructive tool calls, you log everything, and you let it reach external systems via MCP.

Goal

Take the v05 agent and add the operational layer. Stream tokens for live progress, retry on rate-limit/5xx, gate the publish_page tool behind explicit user approval, write a structured event log, and outline how to swap a local tool for an MCP-backed one.

1. Streaming — UI feels alive

A landing page takes 5-15 seconds to generate. Without streaming, the user sees a spinner. With streaming, they see text appearing. The difference between "is it broken?" and "this feels fast" is about ten lines of code. 

const stream = client.messages.stream({
  model: DEFAULT_MODEL,
  max_tokens: 4096,
  system,
  tools: TOOLS,
  messages,
});

stream.on("text", (delta: string) => {
  process.stdout.write(delta);   // live text → terminal
});

stream.on("inputJson", (delta: string) => {
  // tool inputs come in too — for HTML, this is a stream of code
});

const finalMessage = await stream.finalMessage();
// finalMessage.content, .stop_reason, .usage — same as messages.create

In a web app, you'd push these events through SSE or WebSockets to the browser. The shape is the same: render the deltas as they arrive; collapse the final message into your conversation log when the stream ends.

2. Retry — graceful under rate limit

At any meaningful traffic, you'll hit a 429 (rate limit), a 503 (overloaded), or a transient network error. Production agents retry these automatically. Don't retry 4xx errors that aren't 429 — those are bugs. 

async function withRetry(label: string, fn: () => Promise, max = 4): Promise {
  let lastErr;
  for (let attempt = 1; attempt <= max; attempt++) {
    try {
      return await fn();
    } catch (err) {
      const e = err as { status?: number; message?: string };
      const retryable =
        e.status === 429 ||
        (e.status ?? 0) >= 500 ||
        /ECONNRESET|ETIMEDOUT|fetch failed/i.test(e.message ?? "");
      if (!retryable || attempt === max) throw err;

      const wait = 250 * Math.pow(2, attempt - 1);   // 250, 500, 1000, 2000
      await new Promise(r => setTimeout(r, wait));
      lastErr = err;
    }
  }
  throw lastErr;
}
Idempotency matters

Wrapping a messages.create in retry is safe — they're idempotent from your side. Wrapping a publish_page in retry might publish the same page twice. For non-idempotent tools, use the Anthropic SDK's request-level x-idempotency-key header or your own dedup logic.

3. Gated tools — the user has to approve

Some tools shouldn't fire without explicit human approval — publishing a page, sending an email, charging a card. Production agents put a gate in front of these tools that pauses the loop and asks the user.

In a CLI this is a readline prompt. In a web app, it's a button. In Claude Managed Agents, the mechanism is a first-class event: user.tool_confirmation. The agent emits a tool_use with a confirmation_required: true flag, your app receives the event, the user clicks yes/no, and you send back the confirmation event. The agent's loop resumes from there. 

if (block.name === "publish_page") {
  const ok = await gateConfirm(block.name, block.input);
  if (!ok) {
    results.push({
      type: "tool_result",
      tool_use_id: block.id,
      content: "User declined to publish. Don't try again unless asked.",
      is_error: false,
    });
    continue;
  }
}
// otherwise → run the tool

4. Observability — write down what happened

When the agent does something surprising, you need a record. The simplest version is structured JSON written to disk: 

events.push({ ts: Date.now(), kind: "model_turn",  stop_reason, usage });
events.push({ ts: Date.now(), kind: "gate",        tool, approved });
events.push({ ts: Date.now(), kind: "tool_ok",     tool });
events.push({ ts: Date.now(), kind: "tool_err",    tool, message });

await writeFile("out/09-trace.json", JSON.stringify(events, null, 2));

In a real deployment this lands in your observability stack — a log shipper, a database, Sentry, an analytics warehouse, whatever you use elsewhere. The Claude Managed Agents console gives you the full event stream for every session by default — every tool call, every Bash command, every skill file the agent loaded. That's the ceiling for debugging an agent. The trace.json above is the floor.

5. MCP — calling out to real systems

Everything we built so far runs locally. To publish to a real landing-page host, you'd swap the mocked publish_page for a call to HTMLPub's MCP server. The agent doesn't have to change at all — only the tool implementation.

MCP (Model Context Protocol) is the standard for hooking agents up to external systems. The HTMLPub MCP server exposes tools like create_page, upload_asset, list_sites — the same things you'd call from a script. The Claude Managed Agents platform lets you attach MCP servers directly to an agent's configuration; the agent gets those tools the same way it gets your in-process ones. 

# In your agent config (Chapter 10):
mcp_servers:
  - url: https://htmlpub.com/mcp
    auth_vault_id: vault_...          # OAuth token held server-side
The Deal Desk pattern

The production-ready-agent workshop builds a similar architecture for M&A diligence: a coordinator agent that fans out to four parallel research sub-agents, reads from a memory store, reaches Linear over MCP, holds the user's Linear token in Vault, and emits a streaming UI of every event. Every primitive in that stack is accessible from the SDK; the managed-agent platform mostly removes the infrastructure you'd otherwise build.

Try it

bun run stream "vegan meal kits for busy parents"

You'll see HTML stream live to the terminal, then a confirmation prompt before publish:

<!doctype html> <html lang="en"> <head> <meta charset="utf-8"> … GATE: agent wants to call publish_page({"title":"FreshLeaf"…}) approve? [y/N] _

Try answering "n" — the agent will accept the decline and end. Try "y" — you'll get a (mocked) public URL.

Checkpoint
Your publish_page tool takes ~3s to return on a good day, but sometimes the upstream API is slow and it returns after 30s. You wrap it in withRetry with 4 attempts. What's wrong with that?
The rule of thumb: retry the messages.create call all you want; retry tools only if you've reasoned about idempotency. A retry of publish_page after a slow-but-successful first attempt is a duplicate publish that bypasses the user's gate. The Anthropic SDK supports x-idempotency-key headers; many MCP-exposed tools accept an explicit idempotency_key input.
