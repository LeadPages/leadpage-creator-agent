CHAPTER 10·~25 min·workshop: ship-your-first-managed-agent

Ship it

Take the agent you built on your laptop and deploy it as a Claude Managed Agent — a hosted runtime that handles sessions, sandbox execution, MCP routing, and confirmations for you. Same architecture you wrote in Chapter 09, less of it on your servers.

Goal

Understand the four primitives — Agent, Environment, Session, Events — and how each one maps to something you already wrote. Walk through the deploy code, even if your org doesn't have access to the beta yet, so you can see what the platform takes over from you.

The four primitives

┌────────────────────────────────────────────────────────────┐
│                                                            │
│   AGENT          ENVIRONMENT       SESSION      EVENTS     │
│   ─────          ───────────       ───────      ──────     │
│   "what it is"   "where it runs"   "one chat"   "messages" │
│                                                            │
│   model          sandbox files     resources    user.msg   │
│   prompt         allowed egress    memory       tool_use   │
│   tools          MCP allowlist     start time   confirm    │
│   skills                           ...          asst.text  │
│   sub_agents                                     ...       │
│                                                            │
└────────────────────────────────────────────────────────────┘
PrimitiveWhat you wrote in the SDK chaptersWhat CMA gives you
AgentA bunch of constants in shared/prompts.ts and tools in your code.One named, versioned configuration. Updateable independently of any session.
EnvironmentFiles on disk; whatever the OS lets you read.An isolated container per session, with controlled data files and an egress allowlist.
SessionAn array of messages in memory; vanishes when the script exits.A first-class resource you can list, retrieve, attach memory to, and stream events from later.
EventsJSON you pushed into your trace.json by hand.An ordered, durable, replayable event stream — the same one the Console shows you.

The deploy, end to end

The Anthropic ant CLI ships a series of commands that mirror these primitives. Here's what creating and running your agent looks like from the terminal: 

# 1. Create the agent (system prompt + tools + skills + sub-agents)
ant beta:agents create < agent.yaml
# ✓ agent_01HZ4VK7B…

# 2. Create the environment (sandbox config + data files)
ant beta:environments create < environment.yaml
# ✓ env_01HZ4VK7…

# 3. (Optional) Create a memory store
ant beta:memory-stores create --name "leadpage-brands"
# ✓ mem_01HZ4VK7…

# 4. Start a session with a user message
SES=$(ant beta:sessions create \
  --agent agent_01HZ4VK7B… \
  --environment-id env_01HZ4VK7… \
  --resource '{"type":"memory_store","memory_store_id":"mem_…","access":"read_write"}' \
  --title "vegan meal kits, FreshLeaf" \
  --format json | jq -r .id)

# 5. Send the first event
ant beta:sessions:events send --session-id "$SES" \
  --event '{"type":"user.message","content":[{"type":"text","text":"Make me a landing page for vegan meal kits for busy parents."}]}'

# 6. Watch the response stream
ant beta:sessions:events stream --session-id "$SES" --max-items -1 --format pretty

The same thing from the SDK

The CLI commands map one-to-one onto SDK methods on client.beta. The deploy script in your project is a runnable version of the same flow — annotated heavily so you can read it before you have access: 

// 1. Create the agent
const agent = await client.beta.agents.create({
  name: "leadpage-creator",
  model: "claude-sonnet-4-6",
  system_prompt: "You design and write landing pages.",
  skills: [
    { name: "conversion-copy", content: conversionCopy },
    { name: "hero-patterns",   content: heroPatterns },
  ],
  tools: [
    {
      name: "publish_page",
      description: "Publish to htmlpub.com — gated.",
      confirmation_required: true,
      input_schema: { type: "object", properties: { … } },
    },
  ],
  mcp_servers: [
    { url: "https://htmlpub.com/mcp", auth: { vault_id: "vault_…" } },
  ],
});

// 2. Environment
const env = await client.beta.environments.create({
  name: "leadpage-creator-env",
  allowed_network_egress: ["htmlpub.com"],
});

// 3. Memory store (optional)
const mem = await client.beta.memoryStores.create({ name: "leadpage-brands" });

// 4. Session
const session = await client.beta.sessions.create({
  agent_id: agent.id,
  environment_id: env.id,
  resources: [{ type: "memory_store", memory_store_id: mem.id, access: "read_write" }],
});

// 5. Send + 6. Stream
await client.beta.sessions.events.send({
  session_id: session.id,
  event: { type: "user.message", content: [{ type: "text", text: "Make me a page…" }] },
});

for await (const event of await client.beta.sessions.events.stream({ session_id: session.id })) {
  if (event.type === "assistant.text_delta") process.stdout.write(event.text);
  if (event.type === "tool_confirmation_required") { /* approve... */ }
}
Beta surface

The Managed Agents API is in beta as of CWC 2026. Field names and method shapes can shift before GA — check platform.claude.com/docs/en/managed-agents for the current schema. The TS file in src/10-managed-agent.ts has @ts-expect-error on the beta methods so it'll still typecheck against today's SDK.

What CMA does for you, concretely

You had to write…CMA does…
An agent loop with retries and a tool_use_id bookkeepingHosts the loop; you push events in, events come back out.
A sandbox to run agent-generated code inPer-session container with code execution; you set the egress list.
Storage for sessions + the ability to resume laterSessions are first-class resources, listable, retrievable, replayable.
A Vault for OAuth tokens you don't want in env varsVault primitive; agents reference tokens by vault_id, never see the value.
An events viewer for debugging the agent's behaviorThe Console shows every session's full event timeline, including tool calls and skills loaded.
A way to deploy sub-agents with their own threads + observabilitysub_agents field on the agent config; each invocation creates its own thread you can click into.

SDK or Managed Agents — when which?

Pick…When…
SDK onlyYou want to host the agent in your own service, alongside your own auth and data path. You don't need a sandbox. You're comfortable owning the event log and session DB.
Managed AgentsYou want sandboxed code execution, observable sub-agents, a Console for debugging, and the Memory/Dreaming primitives without building them. The trade-off is your agent's lifecycle moves to Anthropic's side.
BothCommon: SDK in your own backend for routing, persistence, and per-user logic — calling out to a Managed Agent for the agent loop itself.

  2. The tool layer (function calling, the agent loop, the gate pattern).
  3. The skill layer (instructions on demand, the load_skill pattern).

  8. The production layer (streaming, retries, gates, observability, MCP).

Checkpoint
In your SDK loop, you wrote messages.push({role:"user", content: tool_results}) on every turn. What corresponds to that step on the Managed Agents side?
On the SDK side, the loop is in your code: you fetch a response, you execute tools, you push the results back, you call again. On the Managed Agents side, the platform runs that whole loop — including the tool-result bookkeeping — inside the session. You only see the inbound and outbound events (user.message, assistant.text_delta, tool_confirmation_required, etc.). That's the main thing CMA does for you: it owns the loop.
